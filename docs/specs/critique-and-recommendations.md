# Критика идеи, фактчек research.md и список рекомендаций

**Дата:** 2026-06-17  
**Источники:** анализ спека, фактчек через WebSearch/WebFetch, два независимых агента (технический и продуктовый)

## ЧАСТЬ 1: Критика идеи

### 🔴 Проблема 1: Шаг 6 — ты делаешь бесплатный сайт до продажи

Это самая большая архитектурная ошибка идеи.

Ты строишь полноценный рабочий сайт и деплоишь его на хостинг — **до того, как клиент заплатил что-либо**. Это инвертированная бизнес-модель.

Что происходит в реальности:
- Клиент получает ссылку на живой сайт → говорит "спасибо, не надо" → уходит с бесплатным продуктом
- Claude сгенерирует плохой HTML → ты будешь дебажить вместо того чтобы продавать
- 60–70% клиентов откажутся на этапе "сколько стоит" — и ты потратил час на сайт в мусор

**Что делать:** заменить шаг 6 на **мокап/концепцию** — скриншот референса похожего сайта, 3–5 блоков схемы структуры, цветовая палитра. Живой сайт — после подписания договора и предоплаты 50%.

---

### 🔴 Проблема 2: "Пиксель-в-пиксель" — это невозможно

Claude работает с текстом, не с пикселями. "Пиксель-в-пиксель копирование дизайна" — это маркетинговая формулировка, которая не имеет технической реализации.

Что реально происходит: Claude читает HTML-текст и генерирует новый HTML, стараясь воспроизвести структуру. Внешние шрифты, CDN-ресурсы, JS-анимации, relative-пути к картинкам — всё это сломается после деплоя.

Реальный результат: "визуально похоже" в 60–70% случаев, "сломано" в 30–40%.

**Что делать:** убрать это обещание из спека. Написать честно: "AI воспроизводит структуру и стиль дизайна". Принимать только inline HTML (всё в одном файле, без внешних зависимостей).

---

### 🔴 Проблема 3: 2ГИС и Instagram не парсятся через WebFetch

**2ГИС** — это SPA на React. При WebFetch придёт пустой HTML-шаблон. Все данные грузятся через приватный API с ротируемыми токенами. WebFetch + Cheerio здесь не работает от слова совсем.

**Instagram** — с 2019 года полностью закрыт для серверных запросов без авторизации. Любой fetch → редирект на login. Это нарушение ToS + юридические риски.

**ВКонтакте** — работает через официальный API, но требует сервисный токен и разные методы для групп/страниц/профилей.

Это случится на первом же тесте с реальной ссылкой из 2ГИС.

**Что делать:**
- 2ГИС: официальный API (бесплатный тир, 1000 запросов/день)
- Instagram: убрать из V1 полностью
- ВКонтакте: реализовать через VK API с сервисным токеном
- Сайт компании (URL): работает через WebFetch + Cheerio — это основной источник

---

### 🔴 Проблема 4: Конверсия 30% — это фантастика

Реальные цифры холодных продаж в сегменте "малый бизнес + сайт":
- Ответ на холодное сообщение (вообще любой): 5–15%
- Выход на разговор: 2–8%
- Сделка: 1–3%

30% конверсия в ответ достигается только при: реферале, входящем запросе, или предварительном касании.

После 10 холодных КП без ответа — мотивация использовать бот обнулится.

**Что делать:** 
1. Поставить реальный KPI: 10% ответов, 3% сделок
2. Изменить флоу: сначала **2-строчный "пинг"** (не КП), потом — только заинтересованным полное КП
3. Добавить трекер воронки: отправлено → ответили → созвон → сделка

---

### 🟡 Проблема 5: Шаг 5 (ChatGPT) сломает весь ритм

Посередине автоматического флоу — ручной шаг в другом инструменте: переключиться в ChatGPT, написать промпт, сгенерировать, оценить, исправить, экспортировать HTML, вернуться в бота, отправить файл.

Это минимум 20–40 минут нестабильной работы. Бот ждёт неизвестно сколько — пока ты не вернёшься (может через час, может через день).

Именно этот шаг определяет качество финального КП. Самое важное место — самое нестабильное звено.

**Что делать:** Либо встроить генерацию дизайна через API (Claude умеет делать HTML), либо принять что шаг 5 — осознанный творческий перерыв, и проектировать флоу так чтобы "пауза на дизайн" не нарушала состояние машины.

---

### 🟡 Проблема 6: 6 ручных точек = это новая бюрократия, не освобождение

Считаем где Александр должен что-то делать:
1. Найти компанию и скинуть ссылку — **ручная работа**
2. Утвердить бриф (шаг 3) — **решение + время на чтение**
3. Сгенерировать дизайн в ChatGPT (шаг 5) — **20–40 минут**
4. Прислать HTML-файл — **ручная работа**
5. Согласовать КП (шаг 8) — **решение + время на проверку**
6. Скопипастить скрипты и отправить — **ручная работа**

Бот автоматизирует технические задачи, но оставляет все точки переключения контекста. Это не "освободить время" — это добавить управленческий слой над ручными операциями.

**Что делать:** Цель V2 — максимум 2 точки касания: ссылка + финальное "отправить". Для V1 — сделать каждую ручную точку максимально быстрой (умные дефолты, краткие саммари для одобрения, не читать полный HTML).

---

### 🟡 Проблема 7: Follow-up системы нет — а это 80% продаж

КП отправлено. Тишина 3 дня. Что дальше? В текущем спеке — ничего.

80% продаж происходит после 2–5 касаний. Бот генерирует КП и останавливается. Это как положить удочку и уйти домой.

Скрипты для копипаста (шаг 9) — это полумера без напоминаний и трекинга.

**Что делать:** Добавить минимальный CRM: статус по каждому лиду + автоматическое напоминание "прошло 3 дня — вот текст follow-up, отправить?" через бота.

---

### 🟡 Проблема 8: Целевой клиент выбран неточно

"Малый бизнес из 2ГИС без сайта" — это не однородная группа:
- Шиномонтаж с очередью на 2 недели — сайт объективно не нужен
- Магазин где владелец 55+ — не поймёт зачем
- Уже пробовали сайт, не сработало, не верит в идею
- Есть сайт на Wix — "и так нормально"

Холодное КП на разработку сайта в 2025 году встречает стену скептицизма.

**Что делать:** сегментировать цель. Искать не "без сайта", а **"с активной рекламой в 2ГИС + без сайта или с сайтом 5+ лет"** — это люди, которые уже тратят деньги на привлечение клиентов и понимают ценность.

---

### 🟡 Проблема 9: Система памяти — минимальна

Спек требует "мощную систему памяти" (твои слова), но в спеке только SQLite с историей проектов. Нет:
- Обучения на результатах: какие типы бизнесов отвечают? Какие КП закрываются?
- Накопленного знания о клиентах: исследовал эту нишу 3 раза — почему переисследовать?
- Паттернов правок Александра: что он всегда меняет — брать в дефолты
- Базы возражений с ответами, которая растёт с каждой сделкой

**Что делать:** В модели данных добавить: `outcome` (ответил/созвон/сделка/отказ), `reason` (причина отказа), `industry`. Агент должен учиться на этих данных.

---

### 🟡 Проблема 10: Нет обработки ошибок вообще

Что происходит если:
- Netlify API упал в середине деплоя?
- Компания не найдена в интернете?
- Claude сгенерировал невалидный HTML?
- Пользователь прислал картинку вместо HTML?
- Telegram webhook доставил сообщение дважды?

В спеке это не описано. В реальности каждое из этих событий случится в первую неделю.

**Что делать:** Добавить раздел "Error handling" в спек с конкретными сценариями и поведением бота в каждом.

## ЧАСТЬ 2: Фактчек research.md

### ❌ ЛОЖЬ: UpHunt — трёхмодульная система для фрилансеров

В research.md написано:
> "Три модуля: Opportunity Discovery, Client Research & Qualification, Personalized Proposal Generation"

**Факт (проверено WebFetch uphunt.io):** UpHunt — это инструмент **специально для Upwork**. Реальные модули: Configure (фиды), Score (AI оценка вакансий), Apply (автоотправка заявок). Никакого "research компании" или "qualification" — только скоринг Upwork-объявлений.

Описание в research.md — это реконструкция как "должно работать", а не как оно работает на самом деле.

**Вывод:** Пример 5 (UpHunt) в research.md не соответствует реальному продукту. Полезный паттерн (исследование → предложение) корректен концептуально, но приписан не тому инструменту.

---

### ❌ НЕ ПОДТВЕРЖДЕНО: "КП в 24 часа = x3 конверсия (PandaDoc)"

В research.md:
> «КП, отправленные в течение 24 часов после разговора, закрываются в **3 раза чаще**»

**Факт (проверено WebSearch):** Эта конкретная статистика "3x close rate в 24 часа" не нашлась ни в одном верифицированном источнике PandaDoc. PandaDoc заявляет об "увеличении close rate на 18%" и других цифрах, но конкретная "3x" формулировка с "24 часами" — либо маркетинговое преувеличение, либо не подтверждённая третьими сторонами цифра из их собственного "State of Proposals" отчёта (который они сами и составляют).

**Вывод:** Использовать идею скорости = конверсия правомерно (это здравый смысл), но конкретную цифру "3x" приводить не стоит — она не верифицирована независимо.

---

### ❌ ВЫДУМКА: "По данным OpenAI, few-shot улучшает качество на 40-60%"

В research.md:
> По данным OpenAI, это улучшает качество на "40-60% по сравнению с нулевым выводом"

**Факт (проверено WebSearch):** Никакой официальной публикации OpenAI с цифрой "40-60% improvement from few-shot" не существует. GPT-3 paper ("Language Models are Few-Shot Learners") показывает улучшение с масштабом, но конкретного процента "40-60 для качества КП" — нет. Это синтетическое число.

**Вывод:** Удалить цифру. Заменить на: "few-shot prompting с примерами реальных КП стабильно улучшает релевантность вывода — это практически доказано опытом, а не конкретным числом".

## ЧАСТЬ 3: Технические проблемы (из технического агента)

Это проблемы которые убьют проект на этапе первого теста:

**Блокеры (без исправления не запустить):**

1. **Railway SQLite без Volume = потеря данных при каждом редеплое** — Railway ephemeral filesystem. Решение: Railway Volume ($0.25/GB/мес) или Turso (облачный SQLite, бесплатный тир).

2. **Netlify deploy асинхронный** — после POST на `/deploys` сайт готов через 30–120 сек. Без polling `deploy.state` бот присылает URL пока сайт ещё 404. Обязателен polling loop.

3. **Netlify: создание сайта ≠ деплой** — в спеке описан один запрос, реально нужно два: `POST /sites` (получить site_id), потом `POST /sites/{site_id}/deploys`. Падение между ними = зависший проект.

4. **Пользователь пришлёт скриншот вместо HTML** — нет валидации типа файла. Claude получит изображение и сгенерирует приблизительный HTML, а не копию. Нужна проверка MIME-type + явная инструкция в боте.

5. **Telegram дубли** — grammy может получить одно сообщение дважды (это нормально). Без идемпотентности создадутся два проекта. Решение: grammy session с deduplification.

**Высокий приоритет:**

6. **2ГИС = SPA** — через WebFetch придёт пустой HTML. Нужен официальный API 2GIS (есть бесплатный тир, 1000 req/day, документация на dev.2gis.ru).

7. **Instagram = убрать из V1** — технически невозможно без нарушения ToS.

8. **Формы на превью-сайте** — без явного указания в промпте Claude сгенерирует `action="#"`. Решение: использовать Netlify Forms (`data-netlify="true"`) — работает автоматически на статическом деплое.

9. **Правки в HTML = expensive** — 100KB HTML = ~25K токенов = ~$0.075 за один вызов Claude при каждой итерации правок. Нужно ограничить количество итераций (максимум 3) и хранить версии.

10. **CSS relative пути сломаются** — если в присланном HTML есть `href="./styles.css"` — на Netlify это сломано. Решение: принимать только self-contained HTML (всё inline) или парсить и инлайнить CSS перед деплоем.

## ЧАСТЬ 4: Лучшие находки из исследований (что точно брать)

Несмотря на критику, вот что в research.md реально ценно и подтверждено:

**1. Паттерн "Telegram-кнопки одобрения" (n8n Auto-Bid Bot)**
Это самая правильная архитектура для такого инструмента. Человек в петле, но минимально. Кнопки вместо текстовых ответов — снижают трение.

**2. Few-shot промпт с реальным примером КП**
Включить `kp-u-yulii.html` как часть системного промпта. Работает — это доказано практикой, даже без цифр OpenAI.

**3. Первое сообщение = конкретная боль (Gigradar)**
"Заметил, у вас нет формы заявки на мобильном — теряете клиентов" работает в разы лучше "привет, я делаю сайты". Это единственный формат холодного outreach с шансом на ответ.

**4. КП как живая веб-страница, не PDF (Qwilr)**
Ссылка на Netlify = клиент видит актуальную версию, можно обновить после отправки, аналитика, удобно на мобильном. Правильное направление.

**5. Скорость = конверсия**
Даже без конкретной цифры "3x" — интуитивно верно. КП отправленное через час после "находки" компании эффективнее чем через 3 дня. Это должен быть KPI системы.

- [ ] **R-16: CRM-минимум** — поле `outcome` в модели Project (sent / replied / call / deal / rejected) + `/status` команда.
- [ ] **R-17: Follow-up напоминания** — через 3 и 7 дней после отправки КП: "клиент ещё не ответил — вот текст напоминания, отправить?" Без этого бот = документогенератор.
- [ ] **R-18: Пинг перед КП** — бот генерирует 2-строчное первое сообщение (от конкретной боли клиента), Александр отправляет. Полное КП — только тем, кто ответил.
- [ ] **R-19: Трекинг просмотра** — пиксель в HTML КП (1x1 img через Cloudflare Worker) → бот уведомляет "клиент открыл КП 10 минут назад". Момент для звонка.
- [ ] **R-20: Обучение на результатах** — агент анализирует: какие ниши отвечают, какие цены принимают. Использует в следующих КП. Это "мощная система памяти" о которой ты говоришь.
- [ ] **R-21: Error handling раздел в спеке** — описать поведение при: Netlify timeout, компания не найдена, невалидный HTML, Claude timeout.

### Три главных изменения которые сделают идею сильнее (из продуктового агента)

**1. Убрать шаг 6 (живой сайт) → заменить мокапом**
Это уберёт самый трудоёмкий и рискованный шаг. КП станет быстрее, проще и без риска сделать бесплатную работу в никуда.

**2. Добавить воронку + follow-up (R-16, R-17)**
Без трекинга результатов бот — генератор документов в пустоту. С трекингом — инструмент продаж который учится.

**3. Изменить флоу: пинг → КП, не сразу КП (R-18)**
Сначала 2 строки о конкретной боли. Потом — только заинтересованным полное КП. Это поднимет реальную конверсию КП с 5% до 20–30%, потому что его будут получать уже тёплые контакты.

## Итог: что в идее правильно

Несмотря на критику — ядро идеи ценное:

1. Исследование компании до написания КП — правильно, это то чего нет у конкурентов
2. Персонализированные скрипты от конкретной боли — правильно
3. КП как живая HTML-страница (не PDF) — правильно
4. Human-in-the-loop с кнопками одобрения — правильно
5. Уникальный дифференциатор (ссылка из 2ГИС → КП) — есть, нет аналогов

Нужно убрать избыточное (живой сайт, Instagram), исправить нереалистичные ожидания (конверсия 30%), добавить недостающее (follow-up, трекинг), и зафиксировать технические блокеры до начала разработки.
